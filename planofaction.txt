### 8. Authentication/session architecture

Authentication uses Supabase Auth with:

```text
components/auth-provider.tsx
lib/db/client.ts
lib/db/server.ts
lib/db/middleware.ts
middleware.ts
```

Client flow:

1. Supabase restores or establishes the session.
2. `AuthProvider` obtains the current user.
3. `get_my_auth_context()` is called.
4. Roles and permissions are stored in React state.
5. UI permission checks use that state.

Server flow:

1. Server code calls `supabase.auth.getUser()`.
2. Server authorization helpers call `get_my_auth_context()`.
3. Server Actions check the returned roles/permissions.
4. RLS independently evaluates database access.

Current architecture does not yet have a separate automated test harness for:

- Authenticated Supabase users
- Role assignment
- Permission assignment
- Session restoration
- Auth context resolution
- RLS execution under different users

Important for this testing track: authentication should remain unchanged initially. Tests should exercise the current architecture rather than redesigning it.

## C. Proposed Architecture

The recommended repository-specific architecture is:

```text
                    ┌──────────────────────┐
                    │       Playwright     │
                    │   Browser E2E tests  │
                    └──────────┬───────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────┐
│              Next.js test application             │
│       Same app code, test environment variables   │
└───────────────────────┬──────────────────────────┘
                        │
                        ▼
┌──────────────────────────────────────────────────┐
│        Local Supabase-compatible environment      │
│                                                  │
│  Auth / GoTrue    REST API    Realtime    Storage │
│          │            │          │          │     │
│          └────────────┴──────────┴──────────┘     │
│                         │                        │
│                         ▼                        │
│                    PostgreSQL                    │
│             migrations + deterministic seed       │
└──────────────────────────────────────────────────┘
```

Testing layers should use the same database foundation:

```text
Unit tests
  → pure TypeScript functions

Integration tests
  → Supabase client/server helpers
  → isolated test database

RBAC/auth-context tests
  → seeded Supabase users and roles
  → current get_my_auth_context RPC

RLS tests
  → authenticated Supabase clients for each test user
  → database policies tested directly

E2E tests
  → Next.js app + local Supabase
  → Playwright browser

Performance tests
  → separate large dataset
  → isolated database or resettable performance environment
```

The initial architecture should preserve the existing auth model:

- Supabase Auth remains the identity provider.
- `get_my_auth_context()` remains the source of current auth context.
- No JWT redesign should be introduced during Phase 0 or the first implementation milestone.
- Tests should verify current behavior before any optimization is considered.

## D. Testing Layers

### Unit tests

Target pure logic with no database:

- Permission helper functions
- Role-to-permission mappings
- Enquiry validation
- Customer/PAN/GST validation
- Search parameter normalization
- Quotation calculations
- Export transformations
- Status transition helpers

Recommended runner: Vitest.

Unit tests should be fast and run without Docker.

### Integration tests

Test application/database boundaries:

- Server Actions
- Supabase server client behavior
- Customer creation
- Enquiry creation
- Interaction creation
- Follow-up creation
- Quotation calculations
- Activity logging
- Reference generation
- Error handling

These should run against a reset local Supabase database.

### RBAC and auth-context tests

Create deterministic users for roles such as:

- Admin
- Sales Manager
- Salesperson
- Customer Service
- Pricing
- Operations
- Accounts

Verify:

- `get_my_auth_context()` returns expected identity
- Roles are correctly resolved
- Permissions are correctly resolved
- Multiple roles combine correctly
- Inactive users are rejected or restricted correctly
- Unauthorized Server Actions reject requests
- Client-visible permission state does not replace server authorization

Passwords may exist only as ephemeral test fixture values in the test environment. They must never be committed as real credentials or stored in production systems.

### RLS tests

RLS tests should use separate authenticated Supabase clients for each seeded test user.

Verify:

- Salesperson sees only permitted enquiries/interactions
- Sales Manager sees team-scoped records
- Admin sees all permitted records
- Customer Service sees assigned records
- Unauthorized inserts fail
- Unauthorized updates fail
- Unauthorized deletes fail
- Cross-user data access is blocked
- RLS cannot be bypassed through client-submitted IDs
- Service-role access is used only by controlled setup/cleanup code

RLS tests must execute against PostgreSQL/Supabase, not mocks.

### E2E tests

Playwright should cover critical user journeys:

- Login
- Logout
- Route protection
- Customer creation
- Enquiry creation
- Customer interaction creation
- Follow-up creation/completion
- Role-specific navigation
- Unauthorized page access
- Search/select workflows
- Export flow
- Validation and error states

E2E tests should use seeded accounts and deterministic data.

### Performance tests

Performance testing should be separate from functional tests.

Targets:

- Customer search with large customer volume
- Enquiry list filtering and pagination
- Interaction list filtering
- Port search
- Permission/RLS query behavior
- Dashboard queries
- Quotation calculation queries
- Bulk export behavior

A large performance dataset should not be loaded into the standard functional test database.

Recommended later tool: k6 or Artillery for HTTP/load testing, plus PostgreSQL query analysis where useful.

## H. Risks

### Authentication/session handling

The current application depends on Supabase Auth sessions and `get_my_auth_context()`. Test helpers must create real authenticated sessions rather than mocking identity for RLS tests.

### Supabase compatibility

Local Supabase versions must remain compatible with:

- Postgres functions
- Auth behavior
- RLS expressions
- Storage policies
- Supabase SSR cookie handling

### RLS testing

RLS can appear correct when tested with a service-role client because service-role access bypasses RLS. RLS tests must use normal authenticated clients.

### Test isolation

Tests must not share mutable records unintentionally. Database reset or transaction isolation will be required.

### Seed ordering

The schema has many foreign keys and role/permission dependencies. Seed order must be:

```text
auth users
→ profiles
→ roles/permissions
→ user roles/role permissions
→ master data
→ workflow data
```

### Migration ordering

Duplicate migration number prefixes require explicit validation before relying on automated database reset.

### Existing repository state

The current worktree already contains many unrelated uncommitted changes. The testing track should be isolated carefully, ideally using a dedicated branch/worktree before implementation begins.

### External services

Attachments, location lookup, email, and other external services may make tests flaky. These should be mocked or replaced with local test doubles in later milestones.

### Production safety

The test harness must prevent accidental use of:

- Production Supabase URL
- Production service-role key
- Real user accounts
- Real customer data

## I. First Implementation Step

The first implementation step should be:

> Add and validate a local Supabase test configuration, then prove that the complete current migration chain can reset successfully against an isolated database.

Specifically, the first implementation should:

1. Confirm whether Supabase CLI is available.
2. Add only the minimum local Supabase configuration required.
3. Validate migration ordering.
4. Run a clean local database reset.
5. Confirm that migrations `001` through `034` apply successfully.
6. Do not add new production functionality.
7. Do not change authentication behavior.
8. Do not add permission caching or JWT redesign.
9. Do not create E2E tests until the database reset is deterministic.

After that baseline is proven, the next step should be a small deterministic auth/RBAC seed and a test for `get_my_auth_context()`.
